Build an AI-Native Coding Studio

Build a production-oriented web application that functions as an AI coding studio similar in concept to v0, Bolt, Replit Agent, and modern agentic IDEs.

The product should allow a user to describe an application in natural language, have an AI coding agent create and modify a real project, execute commands in an isolated environment, preview the running application, inspect errors, automatically fix problems, manage project knowledge, and optionally connect the project to GitHub.

Do NOT build this as a simple AI chatbot that returns code snippets.

The AI must operate on a real persistent project workspace.

OpenWiki

https://github.com/langchain-ai/openwiki

Use OpenWiki as the reference for persistent repository knowledge.

Implement an integrated project-knowledge system that can:

* analyze a repository
* understand its architecture
* generate project documentation
* maintain architectural knowledge as code changes
* expose relevant project knowledge to the coding agent
* avoid forcing the agent to rediscover the entire repository on every request

Use the OpenWiki concepts of a self-maintaining codebase wiki and grounded repository knowledge.

The generated knowledge should live with the project and remain inspectable by the user.

OpenCode

https://github.com/anomalyco/opencode

Study OpenCode as a reference for a serious coding-agent architecture.

Use it for architectural inspiration around:

* agent loops
* file tools
* shell/terminal tools
* permissions
* tool execution
* coding workflows

* interactive agent behavior

Do not simply embed or copy OpenCode wholesale.

Build your own modular agent runtime.

Agent Skills

https://github.com/agentskills/agentskills

Integrate the Agent Skills concept as the extensibility layer for specialized agent capabilities.

Skills should follow the open Agent Skills structure:

skill-name/
├── SKILL.md
├── scripts/
├── references/
├── assets/
└── optional resources

The SKILL.md should contain metadata and instructions.

Implement progressive skill loading:

1. Discover skill name + description
2. Activate only relevant skills
3. Load detailed instructions/resources only when needed
4. Execute skill tools/scripts when permitted

Do not load every skill into the model context on every request.

2. PRODUCT VISION

The product is:

An AI-native development environment where users describe what they want to build and an autonomous coding agent creates, runs, tests, debugs, explains and iterates on the actual application.

Example:

User:

“Build me a modern Solana portfolio dashboard with wallet connection, token balances, transaction history and a dark futuristic interface.”

The system should:

1. Understand the request
2. Inspect the existing project
3. Read relevant project knowledge
4. Create an implementation plan
5. Ask for clarification only when genuinely necessary
6. Create/modify files
7. Install required packages
8. Run the application
9. Run build/tests
10. Inspect errors
11. Automatically fix errors
12. Re-run validation
13. Start/update the preview
14. Show the user the result
15. Explain what changed
16. Continue accepting natural-language changes

The user should feel like they have an AI developer working inside their project.

6. AGENT LOOP

The agent should follow an iterative development loop.

USER REQUEST
↓
UNDERSTAND
↓
READ PROJECT CONTEXT
↓
READ RELEVANT SKILLS
↓
PLAN
↓
EXECUTE TOOLS
↓
RUN PROJECT
↓
OBSERVE
↓
TEST
↓
ERROR?
├── YES → DIAGNOSE → MODIFY → RETEST
└── NO → PREVIEW
↓
REPORT
↓
WAIT FOR NEXT REQUEST

The agent should not stop after generating code.

It should verify that its implementation actually works.

10. SANDBOX

Security is critical.

Never execute arbitrary user-generated code directly on the main application server.

Create a sandbox abstraction:

SandboxManager
├── create()
├── start()
├── execute()
├── install()
├── streamLogs()
├── getPreview()
├── stop()
└── destroy()

Each project should receive an isolated workspace.

Implement resource limits:

* CPU
* memory
* disk
* execution time
* network policy
* process limits

Do not expose host filesystem secrets to generated code.

Design the interface so Docker can later be replaced with stronger isolation such as microVM-based execution.

⸻

11. LIVE PREVIEW

Every running project should be accessible through a secure preview URL.

Example:

https://preview.yourstudio.com/project/

The preview service should:

1. Start the project’s development server
2. Detect the assigned port
3. Proxy traffic securely
4. Stream logs
5. Restart crashed processes
6. Allow the agent to inspect the running application

The preview must be isolated from the main API.

12. ERROR RECOVERY

The agent must be able to debug itself.

Example:

npm run build
↓
TypeScript error
↓
capture stderr
↓
parse error
↓
locate relevant file
↓
read surrounding code
↓
modify file
↓
run build again
↓
success

Limit automatic retries to prevent infinite loops.

After repeated failures, provide the user with:

* what failed
* what was attempted
* relevant error
* recommended next action

23. IMPORTANT ENGINEERING RULES

Do not create fake functionality.

If a feature is not implemented, show it as unavailable rather than pretending it works.

Do not hard-code AI responses.

Do not simulate terminal output.

Do not simulate GitHub operations.

Do not store generated projects only in frontend state.

Projects must persist.

AI modifications must modify actual files.

Terminal commands must execute inside the sandbox.

Preview must run the actual project.

Use proper error handling.

Use TypeScript throughout the backend.

Use clean interfaces between:

UI
API
Agent
Tools
Sandbox
Knowledge
Git
Preview

Make every subsystem replaceable.

24. SUCCESS CRITERIA

The MVP is successful when a user can open the application and do this:

1. Create project
2. Enter:

“Build a beautiful SaaS landing page with pricing, authentication pages and a dashboard.”

3. Agent creates the project
4. Files appear in the editor
5. Agent runs the project
6. Preview opens
7. User says:

“Make the dashboard more futuristic and add a sidebar.”

8. Agent modifies the existing project
9. Preview updates
10. User can inspect the actual code
11. User can run terminal commands
12. User can commit changes
13. Project knowledge is maintained
14. Skills can be activated when relevant
15. The project survives browser refresh/re-login

The final result should feel like:

v0 + AI IDE + coding agent + persistent codebase knowledge + Agent Skills + cloud sandbox + GitHub.

Do not clone another product’s branding or UI exactly.

Build an original product with its own identity and architecture.

First create the complete architecture and implementation plan. Then implement the MVP vertically, ensuring the full flow from:

USER PROMPT → AGENT → FILES → SANDBOX → RUN → PREVIEW → ITERATION

works end-to-end before adding secondary features.
